## 1. 先交付的使用流程

打开本地工作台 → 选择当前重点 → 进入项目 → 返回外部工具处理 → 人工将事项标为待验收 → 核对结果 → 提交验收或记录决定 → 返回更新后的工作台。

这版采用以下约定：

- 管理记录保存在当前本机 profile；会话元数据从使用者明确许可的本机来源只读获取。页面上的外部工具继续独立运行。
- “事项”是统一管理对象，包含项目任务与全局待办。前端使用事项接口，不把旧任务、旧待办再拼成两套数据。
- 首页中间栏命名为“当前重点”；页头可以显示今天的日期，但不把重点解释为今日排期或到期日。
- 右栏“等我处理”有待验收、阻塞、待决策三组。前三者的来源和计数分别计算。
- 第一版不新增数据库字段。缺失的信息显示缺失，不生成看似真实的原因、结果或时间。
- 所有管理写入由使用者操作表单并点击提交触发。选择负责人、关联会话、设置重点均不向 Agent 发指令。

## 2. 页面概念与数据对象

| 页面概念 | 含义与范围 | 数据依据 | 使用者能做的动作 |
| --- | --- | --- | --- |
| 工作台 | 当前选入项目及全局事项的本机总览 | 项目列表、事项列表、决策列表 | 切项目、添加事项、选择重点、进入待处理项 |
| 我的项目 | 已选入工作台且未归档的项目 | `/api/workspace` 的 `projects.items` | 进入项目；原有项目登记与设置入口保留 |
| 当前重点 | 使用者明确关注、尚未完成的事项，可以跨项目 | `focus=1` 且 `state!=done` | 加入/移出重点、修改优先级、进入详情 |
| 项目任务 | 一个项目下的全部事项，不限于重点 | 事项的 `project_id` 等于项目 ID | 新建、修改状态、关联可用会话 |
| 全局事项 | 没有项目归属的事项 | `project_id=null`；兼容历史空字符串 | 保留在首页，显示“全局事项”，也可人工归入项目 |
| 待验收 | 使用者已明确标为等待自己核验的事项 | `state=review` | 查看材料、填写结论、提交验收 |
| 阻塞 | 使用者已明确标为无法继续推进的事项 | `state=blocked` | 查看事项与关联会话、修改状态 |
| 待决策 | 已记录但尚未确定结论的问题 | 决策 `status=open` | 查看备选方案、填写结论并确认 |
| 关联会话 | 从许可来源观察到的外部工具会话元数据，或事项保存的关联键 | 会话接口、`session_key`、`session_link_state` | 查看关联信息；在已有能力支持时返回工具 |
| 项目下一步 | 项目内未完成重点事项的第一项，是展示选择而非独立任务 | 本文第 4 节的排序规则 | 进入该事项；没有重点时引导选择 |
| 验收记录 | 一次人工结论及依据，是追加历史 | `task_reviews`，经 `/api/workspace/reviews` 读写 | 查看历史；不覆盖或删除旧结论 |
| 决策记录 | 问题、选择、理由和备选方案 | `project_decisions`，经决策接口读写 | 编辑草稿、确认、将旧决定标为已取代 |

项目“人工状态”、事项“状态”、决策“状态”、会话“来源状态”是四个不同概念，不能共用一个通用 `status` 文案。项目人工进度不随任务完成自动改写；会话也不替使用者确认任务进度。

## 3. 第一版页面组成

### 3.1 三栏首页

左栏显示项目导航、全局事项入口、项目添加入口和本机工作空间提示。归档和已移出工作台的项目不出现在默认项目导航，保留管理/恢复入口。

中栏显示当前重点、优先级和事项状态；能够从全部可见事项中选入重点。重点为空时显示“选择几件当前要推进的事”，并提供选择或新建入口，不替使用者随机挑任务。第一版不强制只选三件，也不自动清除完成事项的 `focus`：完成后仅从未完成重点列表消失，重新打开该事项时原重点标记仍在。

右栏按“待验收 → 阻塞 → 待决策”固定分组。每项显示项目名/全局标签、标题、对应状态与处理入口。卡片可显示已有时间，但时间未知时显示“时间未知”，不能写成“今天完成”。待决策由独立决策记录承载，不把普通待办当成决策。

### 3.2 项目详情

顶部显示项目名、可用的主目录、项目人工状态和下一步。下方提供任务、会话、决策及验收历史入口。概览可展示摘要，但“查看全部”必须读取所属接口的完整分页，不能使用首页片段替代。

有重点时，下一步显示排序第一项；它可能处于待验收或阻塞，需要显示状态和相应处理入口。有多项同优先级时沿用已有手工顺序。没有重点时显示“尚未选择下一步”，由使用者选定；不以最新更新时间、进程状态或模型推断替代。

### 3.3 事项与验收详情

显示事项标题、项目、人工状态、计划工具、关联会话状态及已有验收记录。第一版没有独立“工具结果摘要”字段，不能把事项标题或验收意见伪装成 Agent 的结果报告。

处于 `review` 时显示人工验收表单：结论、必填理由、可选证据说明和核验勾选项。勾选项默认未勾选，只是本次表单状态；勾选本身不写任务状态，也不表示系统运行过检查。使用者勾选的核验说明可在提交前展示并合入 `evidence`，保存后仍标为人工说明。

提交前展示具体影响，例如“将此事项从待验收改为完成，并新增一条验收记录”。只有点击对应确认按钮才发送 `confirmed=true`。其他状态只展示历史与状态编辑入口，不出现可提交的验收按钮。

### 3.4 决策编辑与历史

草稿表单包含问题、结论、理由、备选方案说明及引用。创建未决定的问题时保持 `open`；填写结论并点击“确认决定”才改为 `accepted`。确认后的正文只读；新方案新建一条记录，旧记录可单独标为 `superseded`。

第一版不把“新建替代决定”和“取代旧决定”包装成一次原子操作：当前接口是两次独立提交，也没有结构化替代关联字段。可以在引用中人工说明关系；只有后一条写入成功才更新旧记录状态。

## 4. 首页范围、排序与计数

这是下一阶段需要实现的页面计算规则，不是已经存在的新聚合接口。

1. 定义可见项目集合 `V`：当前 `/api/workspace` 返回的项目中，`archived=false` 的项目 ID。已被使用者移出的项目不在此集合。
2. 首页事项集合 `I`：来自 `V` 中项目的事项，加全局事项。归档项目、已移出项目以及未登记项目的历史事项不混入默认首页；在原有管理或历史入口中保留。
3. 中栏：从 `I` 中选择 `focus=1` 且 `state!=done` 的事项。`review` 和 `blocked` 重点可以同时出现在右栏，这代表不同入口，不创建第二条事项。
4. 待验收组：`I` 中 `state=review`；阻塞组：`I` 中 `state=blocked`。待决策组：`project_id` 属于 `V` 且 `status=open` 的决策。
5. 三类事项列表按 `priority=0 → 1 → 2 → null` 排序；同级按 `sort_index` 升序、`id` 升序。待决策沿用决策接口的 `created_at` 倒序、`id` 升序。
6. 待处理总数等于三个分组的数量之和；当前重点数独立计算。不能再把重点数加进待处理总数。
7. 项目导航可显示本项目“待验收数 / 阻塞数 / 待决策数”，分别来自以上集合按项目分组后的数量。人工项目进度百分比不参与计算。

现有 `scope=active` 只表示数据库项目未归档，不等于页面可见集合，还会排除全局事项。因此实现时可组合事项的 `scope=active` 和 `scope=global` 查询，再按 `V` 过滤；通过 `id` 去重后合并。决策接口目前没有 active/可见范围参数，需单独按 `V` 过滤。不要直接拿未过滤的 `total` 当作首页数字。

事项接口每页最多 100 条。筛选后的精确总数需要读完相关分页，不能用第一页长度充当总数。加载中显示“读取中”，只完成部分页面时显示“已加载 N 项”或未知总数。事项后续分页须携带第一页的 `list_revision`；两个范围的版本不同或遇到 `list_changed` 时重新读取本轮事项集合，连续变化时保留旧结果并提示刷新，不能无限重试。

项目、事项和决策是分别读取的资源，不承诺跨接口同一时刻快照。决策和验收列表只有普通分页，没有 `list_revision`。各分区保存各自加载状态；刷新失败不把旧内容清成零。未来若数据量或一致性需求超出现有分页能力，再单独设计后端聚合接口。

## 5. 字段来源约定

以下字段是这版会消费、提交或必须避免误用的接口字段，不是整个数据库及所有观察协议的完整字典。

- **人工管理值**：使用者通过工作台写入，保存在当前管理库；不自动从 Agent 输出推断。
- **服务生成值**：服务生成身份、时间或并发令牌，前端读取并原样回传需要的令牌。
- **外部元数据**：许可来源提供的会话或项目元数据。来源缺失、读取失败、截断与未知均保留。
- **展示计算值**：前端按本文计算，不新增数据库列，也不当作现有 HTTP 字段提交。

### 5.1 工作空间与项目

项目列表取自 `GET /api/workspace` 的 `projects.items`。持久化项目主要来自 `projects/project_directories/project_sources`；Codex 项目的部分展示字段由许可元数据投影提供。工作台中只读项目表示外部项目元数据不能在此改写，不表示其本机任务和决策都不可管理。

| 字段 | 含义与页面概念 | 来源与写入边界 | 空值/限制 |
| --- | --- | --- | --- |
| 顶层 `today` | 页头当天日期，`YYYY-MM-DD` | 服务按北京时间生成 | 只作日期展示，不是事项计划日期 |
| 顶层 `sampled_at` | 本次工作空间响应生成时间 | 服务生成 | 不是所有外部来源最新更新时间 |
| `projects.status/reason` | 项目区是否可读及原因 | 服务投影 | 不可用时显示来源错误，不显示空项目结论 |
| 项目 `id` | 稳定项目身份，连接事项与决策 | 管理库登记/已有来源映射；前端只读 | 是不透明字符串，不要求 UUID，不用名称或路径替代 |
| `name` | 导航与项目标题 | 登记值或许可来源投影 | 不作为关联键 |
| `archived` | 是否从默认工作范围归档 | 管理记录；接口为布尔值 | 归档不等于完成，不删除历史 |
| `directories[]` | 已登记的工作目录集合 | 目录登记/许可来源映射 | 只列已许可内容，不扫描其他目录 |
| `directories[].id` | 目录在本项目内的绑定身份 | 登记值/来源映射，`main` 为主目录 | 与项目 ID、会话 ID 不同 |
| `directories[].path`、`root` | 目录路径；`root` 是主目录便捷值 | 登记值/来源投影 | 缺失显示“目录未知”，不能当成可直接执行的命令 |
| `source.kind` | 项目进度观察来源类型 | 来源设置/内部来源投影；`none` 未配置、`wfc` 工作流进度、`text` 文本、`json` 版本化 JSON、`codex` 外部项目标记 | 不代表 Agent 结果或当前负责人；Codex 标记不由普通项目编辑表单写入 |
| `source.directory_id` | 进度来源绑定到哪个已登记目录 | 来源设置，引用 `directories[].id` | 未配置或 Codex 来源标记时为 `null` |
| `source.relative_path` | 进度文件或目录在绑定目录内的位置 | 来源设置；服务校验相对位置，`wfc` 固定为既有工作流目录 | 未配置或 Codex 来源标记时为 `null`；不是允许任意读取本机文件的授权 |
| `read_only` | 外部项目元数据在此不可编辑 | 服务投影，可缺省 | 不据此禁用已有本机事项的状态更新 |
| `source_available/binding_available` | 外部项目来源、绑定是否可用 | 服务根据许可来源计算，可缺省 | 不能据此声称工具正在执行 |
| `manual_recorded` | 是否已有项目人工进度记录 | `project_manual` 是否存在的投影 | `false` 时显示“未记录” |
| `state` | 项目人工状态：未开始、在做、等我、完成 | 人工进度记录；通过原进度接口写入 | 没有记录时为 `null`；不同于事项 `state` |
| `percent` | 人工填写的项目完成百分比 | 人工进度记录 | `null` 表示未填写；`0` 是有效值，不能当缺失 |
| `note` | 项目人工进度说明 | 人工进度记录 | 不是阻塞原因或事项结果的通用容器 |
| `updated_at` | 当前项目投影中的人工进度更新时间 | `profile_projects` 会用人工记录时间覆盖登记更新时间 | 无人工记录时可能 `null`；不能标为“项目最近活动” |
| `manual_reason` | 人工记录缺失原因 | 服务投影 | 用于区分未记录与零进度 |
| `created_at/position` | 项目登记时间与原有导航顺序信息 | 管理库/来源映射；可因来源而缺省 | 沿用接口项目顺序，不用它们推断开发活跃程度 |
| `task_counts` | 项目人工事项状态分布，含 `total/todo/doing/blocked/review/done` | 管理库聚合 | 不含待决策数；不把 `total` 解释为今日任务数 |
| `observation/records/records_available/history_url` | 进度观察与人工历史的既有扩展信息 | 原进度观察及历史接口 | 本轮保留原入口，不将观察通过结果写成验收结论 |
| `sessions` | 项目概览中的有限会话快捷项 | 服务投影，存在数量上限 | 不作为完整会话列表或会话总数来源 |

### 5.2 事项字段

读写使用 `/api/workspace/items` 和 `/api/workspace/items/update`。列表主要来自 `task_items`，再由服务补充项目与关联状态。第一版不使用旧 `/tasks`、`/todos` 返回值重建主列表。

| 字段 | 类型与含义 | 来源与写入边界 | 页面规则 |
| --- | --- | --- | --- |
| `id` | 规范 UUID 字符串；统一事项身份 | 服务生成，只读 | 更新事项、提交验收都用它；不是 `origin_id` |
| `title` | 非空字符串，具体要做的事 | 人工输入；新建最多 2000 字符，旧超长历史按既有兼容规则保留 | 允许换行；卡片可节选，详情可读全文，不能截断后覆盖原文 |
| `project_id` | 项目 ID 或 `null`，历史可有空字符串 | 人工选择；新绑定必须通过现有项目校验 | 空归属显示“全局事项”；未登记历史显示“项目未登记” |
| `provider_id` | 计划负责工具 ID 或 `null` | 人工选择；现有值 `codex/claude/grok/dsh/opencode/hermes/pi` | 标签统一为“计划工具”，不表示指令已发送、工具在线或具备会话接入 |
| `state` | `todo/doing/blocked/review/done` | 人工状态；验收提交可按明确结论更新 | 分别显示待办、进行中、阻塞、待验收、完成 |
| `priority` | 整数 `0/1/2` 或 `null` | 人工输入；事项接口已接通 | 高/普通/低/未设置；未设置排在低之后；布尔值无效 |
| `focus` | 整数 `0/1`，持续重点标记 | 人工输入；事项接口已接通 | 无日期语义，不自动按天清空；布尔值无效 |
| `session_key` | 关联会话键或 `null` | 人工选择当前可关联的会话；现有事项关联只支持经校验的 Codex 会话 | 负责人是其他工具时不能伪造该工具会话关联；解除关联要明确提交 `null` |
| `session_link_state` | `none/verified/not_in_current_sample/project_mismatch` | 服务根据保存关联和当前许可样本计算，只读 | 无关联/关联已核对/当前无法核对/项目不匹配；不等于运行或完成状态 |
| `project_name` | 项目登记名称便捷投影，可 `null` | 服务补充，只读 | 可结合可见项目映射显示；不能把名称回写为关联 ID |
| `project_excluded` | 保存的项目已被移出当前工作台 | 服务计算的布尔值，只读 | 不默认混入首页；历史保留，不自动解除关联 |
| `created_at/updated_at` | 事项登记/最后一次实际变更时间 | 服务 UTC 时间；导入历史可保留旧值或 `null` | 不是外部工作开始/完成时间，也不是计划日期 |
| `revision` | 当前事项并发版本，安全正整数 | 服务生成；实际更新递增，无变更提交不递增 | 提交更新与验收时原样作为 `expected_revision` |
| `sort_index` | 统一事项列表顺序索引 | 服务维护，只读 | 默认顺序及同优先级次序；第一版不提供拖拽写入假接口 |
| `origin/origin_id` | 旧记录类别 `task/todo` 与原始身份 | 迁移/创建时生成，只读 | 用于追溯；`origin_id` 历史上可以是空字符串，不能替代统一 `id` |
| `source` | 事项原有来源标记，可 `null` | 创建/迁移保留，只读 | 不解释为工具结果或验收证据 |
| `todo_position` | 旧待办兼容顺序，可 `null` | 服务/迁移维护，只读 | 新主列表不据此重新排序 |
| `resume_state` | 从完成状态恢复时使用的历史非完成状态 | 服务维护，只读 | 不是下一步，不由前端直接改写 |

创建请求只发送可写字段。事项更新形状为 `{id, expected_revision, changes}`，`changes` 仅含本次明确修改的字段；省略代表保留，不能为方便清空其他字段。标记重点、修改优先级、解除会话关联均使用此规则。

`review → done` 若通过普通状态编辑提交，只改变状态，不生成验收记录。新 UI 在待验收事项的“验收通过”动作必须走验收接口，不能用一次普通改状态冒充验收。

### 5.3 决策字段

通过 `/api/workspace/decisions`、`/api/workspace/decisions/update` 读写，持久化来源是 `project_decisions`。

| 字段 | 含义与取值 | 来源与写入边界 |
| --- | --- | --- |
| `id` | 稳定决策 UUID | 服务生成，只读 |
| `project_id` | 此问题属于哪个项目，必填 | 人工选择当前已登记、选入且未归档项目；创建后不改归属 |
| `title` | 要决定的问题，非空、最多 160 字符 | 人工输入；如“首版采用哪种布局” |
| `decision` | 选定的结论，最多 4000 字符 | 人工输入；草稿可为空，确认决定时必须有内容 |
| `rationale` | 为什么这样决定，最多 4000 字符 | 人工输入，可为空；不自动冒充模型论证 |
| `alternatives` | 其他方案及取舍说明，最多 4000 字符 | 人工输入，当前是一个文本字段，不是结构化方案数组 |
| `status` | `open/accepted/superseded` | 人工明确提交；待决策/已确认/已取代；默认 `open` |
| `links` | 最多 20 条引用字符串，每条最多 2048 字符 | 人工输入；DB 使用 `links_json` 保存，接口返回数组；第一版按文本展示，不自动访问 |
| `created_at` | 记录创建时间 | 服务 UTC 时间，只读；不等于作出决定时间 |
| `updated_at` | 记录最后变更时间，同时是并发令牌 | 服务生成，只读；更新请求原样回传 |
| 请求 `expected_updated_at` | 使用者编辑时所基于的版本 | 从上次读取的 `updated_at` 复制，不由前端自己生成 |
| 请求 `changes` | 本次修改的可写字段子集 | 使用者表单生成；不能修改身份、项目和服务时间 |
| 请求 `confirmed` | 明确提交本次本机写入 | 仅确认按钮触发时发送 JSON `true`；不是持久化字段或身份认证证据 |

`open` 草稿可编辑内容、确认或标记取代；`accepted` 只能保持或变为 `superseded`，不能覆盖正文或重新打开；`superseded` 不能恢复为其他状态。归档/移出项目的历史仍可能由列表接口返回，因此首页需执行第 4 节的范围过滤。

### 5.4 验收字段

通过 `/api/workspace/reviews` 读写，历史来源为 `task_reviews`。只追加历史，不能更新旧结论。

| 字段 | 含义与取值 | 来源与写入边界 |
| --- | --- | --- |
| `id` | 一次验收记录的 UUID | 服务生成，只读 |
| `task_id` | 被验收事项的统一 ID | 从事项 `id` 复制；包括原待办迁移来的事项，不用旧任务 ID |
| 请求 `expected_revision` | 这次验收基于哪个事项版本 | 从最新事项的 `revision` 原样复制；当前验收历史不另存该版本号，不能在历史页面虚构版本快照 |
| `verdict` | `approved/changes_requested/rejected` | 人工选择；通过→完成、要求修改→进行中、拒绝→待办 |
| `reason` | 本次结论与理由，非空、最多 2000 字符 | 人工填写；不是自动读取的工具报告 |
| `evidence` | 最多 20 条核验说明或引用字符串，每条最多 2048 字符 | 人工填写/本次勾选项经确认加入；DB 为 `evidence_json`，接口为数组；可为空，不表示系统验证过 |
| `reviewer` | 可选的人工称呼，最多 80 字符 | 人工标签，可 `null`；不代表已认证身份 |
| `run_id` | 可选外部运行引用，最多 160 字符 | 人工引用，可 `null`；不要求指向本机执行表，也不证明该运行存在或完成 |
| `created_at` | 验收记录保存时间 | 服务 UTC 时间，只读；不是 Agent 结束时间 |
| 请求 `confirmed` | 明确确认此次状态变更和历史追加 | 必须是 JSON `true`；不持久化，不允许页面加载/刷新时自动提交 |
| 响应 `review` | 已保存的验收记录 | 验收接口返回，不含请求并发令牌或确认字段 |
| 响应 `item` | 同一事务更新后的事项 | 当前为存储字段集合，不保证包含列表接口补充的项目名和关联状态；需要刷新事项投影 |

当前事项必须仍为 `review`，且 `expected_revision` 一致。写事务会一起保存验收记录、事项状态和新版本；任一步失败都回滚。再次验收需由使用者先把事项重新标为待验收，再基于新版本提交，不覆盖前次历史。

### 5.5 会话字段与来源状态

第一版项目完整会话列表使用 `GET /api/workspace/codex/sessions`。现有主要接入是 Codex 本机元数据；计划工具列表里存在 Claude Code 等名称，不代表都有同等的会话读取能力。

| 字段 | 含义与来源 | 页面规则 |
| --- | --- | --- |
| `thread_id/session_key` | 外部线程身份及带提供者前缀的关联键 | 由许可来源投影提供，只读；关联事项回传完整 `session_key` |
| `title/title_truncated` | 外部会话标题及是否为节选 | 缺标题显示“未命名会话”，节选保留提示；不是任务结果摘要 |
| `cwd` | 来源声明的工作目录 | 仅作上下文，不以相同路径直接认定可靠关联 |
| `project_id/assignment_state` | 来源投影的项目归属；`assigned/projectless/unknown/conflict` | 分别为已归属/明确未归属/未知/冲突；手工项目的目录匹配按服务既有规则，前端不自行重新判归属 |
| `binding_available` | 本次样本是否允许建立新关联 | 只读，由服务核验；来源缺失、部分样本、归档等情形可能为 false |
| `archived` | 外部工具中的会话归档标记 | 不代表会话已结束或任务完成；`scope=active` 是未归档，不是正在运行 |
| `created_at/updated_at` | 外部会话元数据提供的时间 | 来源提供，显示为“会话创建/更新”，不能标为执行开始/结束 |
| `source_kind` | 外部元数据的记录来源类别 | 沿用接口值，仅辅助追溯，不生成运行结论 |
| `activity_state/task_completion` | 来源可证明的活动/完成状态 | 当前 Codex 投影均为 `unknown`；显示未知，不显示正在执行/已完成 |
| 包装 `status/reason` | `available/stale/not_configured/unavailable` 及固定原因 | 描述读取来源；不映射为事项状态 |
| 包装 `complete` | 是否完整读取本次来源范围 | false 表示部分覆盖；不要声称本机全部会话数量已统计 |
| 包装 `sampled_at/source_id` | 来源采样时间与来源身份 | 只读；采样时间不等于最后一条消息时间；来源变更需丢弃旧分页 |
| 包装 `revision` | 该会话列表的来源版本标识 | 不透明字符串，不等于事项 `revision`；前端分页检测变化后重新读取 |

来源不可用时保留本机事项与决策管理；不新增或重绑无法核对的会话。已有会话关联无法核对时展示原因，不能悄悄解除。只有工具观察接口已提供可用动作及合格窗口时才展示“返回工具”；会话键和 `cwd` 本身不构成可执行导航能力。

### 5.6 列表与展示计算字段

| 字段或计算名称 | 含义与来源 | 写入约束 |
| --- | --- | --- |
| 列表 `items/total/offset/limit` | 当前接口查询范围的记录、数量、偏移、页长 | 服务返回；`total` 不是全部项目/全部本机来源的总数 |
| 事项列表 `list_revision` | 事项集合并发版本，服务安全正整数 | 仅用于事项分页，不用于决策或会话更新 |
| 页面计算“项目标签” | 用项目映射或事项 `project_name` 展示；空归属为全局 | 不提交为新字段 |
| 页面计算“当前重点数” | 第 4 节重点集合的去重数量 | 不持久化、不从 `task_counts.total` 取值 |
| 页面计算“待处理数” | 可见范围内待验收数+阻塞数+待决策数 | 各源未成功加载时不伪造精确总数 |
| 页面计算“下一步” | 当前项目未完成重点中排序第一项 | 不是 `next_step` 字段；不复制成新事项 |
| 表单“核验勾选项/未保存草稿/提交中” | 本页面本次编辑状态 | 不自动写库、不在刷新时冒充已保存；离开未保存表单时提示保留或放弃 |

时间展示统一使用北京时间并标明语义；未知时间保留未知。三个 `revision` 概念不可混用：事项版本控制单条更新，事项 `list_revision` 控制列表分页，会话字符串版本控制来源分页。决策另用 `updated_at` 控制更新。

## 6. 用户动作与读写契约

| 动作 | 实际请求 | 成功后页面行为 | 特别约束 |
| --- | --- | --- | --- |
| 添加事项 | `POST /api/workspace/items`，提交标题及人工选择字段 | 展示服务返回身份与版本，重读所属列表 | 计划工具默认未分配；不发送任务 |
| 加入重点/调整优先级/改状态 | `POST /api/workspace/items/update` | 使用新版本，再刷新关联重点、待处理和项目计数 | 单行轻量操作也应有清晰按钮与反馈；普通改状态不生成验收历史 |
| 标记待验收 | 同上，`changes.state=review` | 进入右栏，提供人工验收入口 | 操作代表人选择等待验收，不代表自动检测到 Agent 完成 |
| 提交验收 | `POST /api/workspace/reviews` | 展示已保存结论，刷新事项、历史与首页；页面自行退出或明确提供返回入口 | 三种结论和影响分别确认；提交中禁用重复提交 |
| 记录待决策问题 | `POST /api/workspace/decisions`，`status=open` | 进入当前项目及右栏待决策 | 不把“保存问题”按钮写成“确认决定” |
| 确认/编辑决策 | `POST /api/workspace/decisions/update` | 使用新的 `updated_at`，刷新分组与历史 | 已确认正文只读；冲突时不覆盖 |
| 标记决定已取代 | 同上，`changes.status=superseded` | 保留历史，展示状态变化 | 新替代决定是另一次独立创建 |
| 查看/返回外部工具 | 复用已有会话与工具观察导航能力 | 显示成功/失败/不可用结果 | 不新增 Agent 执行、发送、审批、取消能力；不承诺精确回到某个标签页 |

请求权限、字段校验和大小限制沿用[接口说明](usage.md#重点优先级决策与验收接口)。服务端是最终校验者；前端不能根据设计稿放宽规则，也不能绕过现有同源与 CSRF 检查。安全令牌仅保留在运行会话内，不写示例、日志或文档。

错误行为统一如下：

- `422`：显示具体字段错误，保留输入；`confirmed` 缺失不能自动补成 true 再重试。
- `404`：说明目标不存在，返回列表刷新；不把用户草稿写到同名新目标。
- `409 item_changed/decision_changed`：保留草稿、读取新版本，让使用者重新核对后再确认；不自动套新版本提交。
- `409 list_changed`：重新读取事项列表，保留正在编辑的表单。`review_state_conflict/decision_closed` 等状态冲突按真实状态禁用操作并说明。
- 网络断开/响应丢失：视为结果未确认，先重新读取当前事项及相应历史核对。当前创建接口没有幂等键，不能自动重发新建决策或新建事项；更新时间戳保护也不能替代该检查。
- 区域读取失败：保留上次内容并标记过期与失败原因，提供重试；“没有数据”“未配置”“读取失败”“部分覆盖”分别展示。

## 7. 当前缺口与第一版取舍

| 设计稿内容 | 现有数据情况 | 第一版处理 | 后续扩展条件 |
| --- | --- | --- | --- |
| 今天排期、到期日 | 没有 `planned_date/due_at` | 使用“当前重点”，只展示当天日期 | 确认需要按日计划、跨日结转后另定字段 |
| 阻塞原因 | 只有 `state=blocked`，没有独立原因字段 | 显示“原因未记录”；保留事项标题、会话入口和人工状态修改，不提供会丢失的原因输入框 | 试用证明必要时增加可保存的原因及状态转换规则 |
| Agent 结果摘要与自动验证报告 | 没有可信的统一结果摘要接口 | 显示“结果摘要未提供”；使用者在外部工具核验，在验收理由/证据中记录自己的结论 | 明确外部结果如何导入、版本与证据来源后再接入 |
| 自动判断 agent 运行结束 | 当前会话活动和任务完成均未知 | 一律显示未知，待验收先人工标记 | 有经过验证的来源协议后再定义观察字段 |
| 独立下一步描述 | 没有 `next_step` 字段 | 从项目重点事项计算，不另存一份 | 确认下一步不能由具体事项承载时再设计 |
| 独立验收清单及每项结果 | 只有理由与字符串证据 | 勾选为表单状态，人工说明可合入证据 | 要求历史中逐项追溯时再定结构化检查项及版本 |
| 独立事项详情 GET | 当前是分页列表及写接口，没有单条详情 GET | 从列表进入保留事项；需要更新时通过项目/全局完整列表按 ID 重新核对；找不到前不把部分页当删除 | 直接链接、刷新恢复或性能要求成熟时补单条读取接口 |
| 决策替代关系 | 没有 `supersedes_id` 或原子替代接口 | 单独记录新决定、单独标记旧决定已取代 | 确认需要可靠关系导航与一次提交时另定事务契约 |
| 完整通用活动流 | 只有部分人工进度历史、决策和验收记录 | 按类别展示真实历史，不生成“所有操作日志” | 需要追溯事项每次编辑时再设计统一事件记录 |

第一版可用不意味着以上信息已经完整。验收页要帮助使用者核验真实外部工作，不能靠填充示例摘要制造闭环完成的印象。

| P0-6 | 完成整体可用性与真实页面验收 | `tests/frontend`、`tests/e2e`；证据留 `work/` | 使用临时 profile 验证完整流程、窄屏、键盘、长标题、未知来源、失败恢复、重复点击与并发冲突；提供真实页面预览 |
| P1-1 | 使用一段实际工作周期，记录仍需跳出页面查找的信息 | 个人使用；记录仅留 `work/` | 观察能否早间选重点、处理中定位项目、收尾清理待处理；不将个人项目或材料写入公开文档 |
| P1-2 | 根据试用证据决定新增字段和读取能力 | `workspace` 业务包及所属 HTTP 装配 | 分别决定是否需要阻塞原因、结果导入、计划日期、单条详情读取、原子替代；有必要才新增 schema/API |

实施新模块或静态资源时须同步资源白名单、打包与相关测试；不建立根前端影子项目。现有 Figma 只是视觉参考，文案与状态展示以本契约和实际来源为准。新增第三方 UI 依赖须另行验证，不把框架迁移混入这一轮闭环。

## 9. 第一版验收场景

1. 在一个新临时 profile 添加两个项目、一条全局事项，为不同事项设置重点和优先级；刷新后记录与顺序保留。
2. 把项目事项分别标为待验收、阻塞，新建一个待决策问题；首页三组计数与项目标签正确，重点与待处理交叉不生成重复记录。
3. 归档一个项目、移出另一个项目，再读取首页；默认范围排除其事项与决策，管理/历史入口仍保留原记录。
4. 构造超过一页的事项与决策，确认计数不取第一页长度；分页中更新事项，页面能处理版本变化而不丢草稿。
5. 审阅一条待验收事项，先核对外部材料，再填写理由并确认通过；事项完成、历史新增、右栏减少。要求修改和拒绝分别回到进行中与待办。
6. 两个页面基于同一版本提交验收或编辑决策，只有合法的新版本写入成功，旧窗口显示冲突并保留草稿。
7. 确认一条决定后尝试修改正文；页面保持只读。新建替代决定与标记旧决定取代分别显示各自成功或失败。
8. 关闭许可会话来源或使其读取失败；本机事项仍可管理，会话显示未配置/未知/过期，不把工具消失当作任务完成。
9. 在保存后模拟响应丢失；页面先读取已有记录核对，不能自动重复创建事项、决定或验收记录。
10. 首屏没有重点、没有待处理时提供清晰入口；窄屏与键盘仍能完成选择重点、打开项目、验收和记录决定。

这些是后续界面的验收要求，不代表本文件创建时已执行页面测试。实际结果必须由实施任务记录命令、退出码、截图和观察到的失败。

## 11. M2 真实执行与事项会话（设计基线）

这一节是 M2 的关系和字段设计基线，不代表已实现；实现前仍需选定首个真实 Agent 并核对官方接口。

### 11.1 六个不同概念

| 概念 | 含义 | 写入方 | 是否占用任务 |
| --- | --- | --- | --- |
| 登记 | profile 中的 Agent 身份、token、adapter/connection | 人 | 否 |
| 连接验证 | 对 Agent 的 handshake/探测结果 | 系统/人触发 | 否 |
| 分配 | `task.assigned_agent_id` | 人 | 否 |
| 派发 | 人确认的 brief 快照、目标 Agent/目录、送达状态 | 人确认，接入模块写结果 | 否 |
| 领取 | Agent 用 token 创建 run | Agent | 是 |
| 运行 | 一次执行，含进度、等待、提交 | Agent | 是 |
| 审核 | 人对本次结果的结论 | 人 | 结束后 |

登记/连接/分配/派发/领取/运行/审核不能共用一个“状态”文案。派发成功不等于 Agent 领取；MCP 工具存在不等于能把消息送进聊天窗口。

### 11.2 关系

```text
项目
  └─ 事项（标题 + brief：原始需求/验收标准/约束/参考）
       ├─ 派发（人确认的快照 + Agent/目录 + delivery_state）
       │    └─ 运行（Agent 领取后的一次执行，最多一个 active）
       │         └─ 审核（人工结论）
       └─ 会话（人与某个 Agent 的交流；可多条，先后不同 Agent）
```

### 11.3 brief 与派发

事项 brief 至少包含：

- 用户原始需求 `request_text`
- 验收标准 `acceptance_text`
- 约束/禁止事项 `constraints_text`
- 参考路径/链接/说明 `references`
- 明确执行目录；多目录项目必须选择，单目录可默认 main

派发记录（`task_dispatches`）保存：目标 Agent、项目、目录绝对路径、brief 完整 JSON 与哈希、人确认的完整发送文本、`delivery_mode=auto|manual`、`delivery_state=previewed|sent|delivered|unknown|failed|cancelled`、外部引用、关联会话、时间。

不变量：

- 用户确认前不写外发；双击/刷新不重复派发。
- 派发后修改事项只影响下一次派发，不静默改变已发送快照。
- 一个事项可先后多次派发；同一 active run 期间禁止新派发。
- `sent` 不等于 `delivered`；`unknown` 不自动重发。
- 自动发送只在工具提供真实接口并验证后启用；否则只能 manual，不假装成功。

### 11.4 会话

事项会话至少包含：任务、项目、Agent、来源 `source`、外部 `external_id`、标题、可打开入口、最近来源时间、本地关联时间。`(source, external_id)` 必须命名空间化，避免不同工具碰撞；一条事项可多段会话，一条会话最多关联一个事项。旧 `session_key` 保留为 legacy 关联。没有正文读取能力时只显示标题元数据，不宣称已同步聊天正文。

### 11.5 运行与审核

- 长任务、工具授权等待、连接未知按现有 A7：不自动失败、不释放占用；等待人显示 `waiting_user`。
- `progress`/`submit-review` 必须带本次 claim 的 `run_id`；旧 run 不能写新 run。
- 工具授权与结果审核分离；工作台不提供伪批准按钮。
- 只有人工审核 `approved` 才 done；退回/拒绝不自动重跑。
- `agent_runs` 可增加 `dispatch_id` / `session_id`，`task_reviews` 可增加 `dispatch_id`；旧记录为空按 legacy 显示。

### 11.6 首个真实 Agent 的决策门

在选定工具前不得开始自动派发。选定后必须记录：调用方向（工作台→Agent 或 Agent→工作台）、触发方式、能否新建/续接会话、授权处理、明确不支持的能力，以及可复现探测证据。当前本机探测没有已验证的自动送达接口；第一版允许 manual 交接 + workbench CLI，并如实标记 `delivery_mode=manual`。

## 12. 下一阶段：执行桥最小 MVP

本节是 M2-08 产品规划。产品目标来自实际使用反馈；两位开发者已对齐首个适配器、复用方向与职责，具体文件范围须经能力审计后确认。它不表示执行桥已经接通，也不授权部署、启动真实项目任务或修改用户的 Agent 配置。

### 12.1 要解决的问题与当前边界

工作台的价值是减少人在多个 Agent 和项目之间搬运信息的负担。下一阶段优先接通执行与反馈，暂停新增无助于闭环的页面、字段和厂商适配。

当前事项、说明快照、Agent 注册、运行上报接口、会话元数据与人工审核已有基础。新建待办或选择 Agent 不会自动把任务送入外部聊天；手动模式仍需复制交接内容。Agent 可以调用 CLI/MCP 自行领取、上报和提交，无需人代写进度，但尚无统一机制保证每次执行都主动反馈。结构化运行事件也尚未统一关联到 Agent 工作台的事项与审核链。

仓库已有 `execution` 所属的受控 Codex 进程、事件与授权处理基础。先审计其与当前事项协议的差距，再复用和连接；不把已有执行模块误称为本次 MVP 已验收，不另建重复的进程管理器。

当前 profile 服务没有装配 `ExecutionService`，执行能力开关关闭；旧执行入口按 `tasks` 及 Codex 来源取任务，尚未接入新的事项/说明/派发协议。已有底层执行记录与 `agent_runs` 分离，必须先打通映射，不能直接在页面宣称“可执行”。

### 12.2 最小 MVP 的用户流程

**一个本机项目、一个支持执行的真实 Agent、一条事项，从人工确认派发到人工验收。**

1. 用户添加项目目录和 Agent，首次完成连接配置与能力检查；页面区分“支持工作台执行”“仅手动交接”“连接不可用”。
2. 用户填写需求、验收标准与目录，核对本次完整快照和权限范围，点击确认执行。未确认的待办不会被自动领取。
3. 工作台通过已验证的适配器启动一次受控运行，将快照送入上下文，并建立事项、派发、运行和来源会话的关联；用户不复制到聊天框。
4. 适配器自动回传真实运行事件，页面呈现开始执行、当前可观察活动、最近事件、等待人或异常。用户不手写阶段和进度；不能观察的部分如实标未知。
5. 真正需要授权或补充信息时，保留运行并提示用户。首个适配器必须有一条经过实测的人机响应路径，回复与对应运行、请求匹配；普通补充文本不能充当工具授权。
6. 执行结束后，适配器自动汇集结果和可取得的验证材料，事项进入待审核。用户查看请求与结果，再选择通过或退回；只有人工通过才进入已完成。

用户日常只承担提出需求、确认执行、处理必要决策和验收。确认范围内的执行记录由系统采集。工具操作是否逐次询问遵守用户选定的权限策略，不能静默扩大权限。

首版可以只支持工作台新建的受控会话，不承诺接管当前桌面聊天。退回修改可以经再次确认启动新运行，不要求先完成任意历史会话的续接；必须携带原验收意见并保留前次结果。

### 12.3 必须具备的能力

| 能力 | MVP 必须做到 | 不可据此推断 |
| --- | --- | --- |
| 执行接入 | 一个真实适配器有明确入口、版本、目录和权限校验，连接诊断可见 | 本机装有程序不等于已可执行 |
| 确认派发 | 人确认的快照对应唯一执行意图，重复点击或响应丢失不会启动两次 | 分配、进程启动不等于接收或领取 |
| 运行与会话关联 | 确认的派发与实际执行、来源会话建立可追踪关系 | PID、聊天标题不能冒充运行身份 |
| 自动反馈 | 运行事件自动持久化，刷新页面仍可见；正常本机条件下事件接收后 5 秒内在页面可见 | 无事件不等于无工作或失败，不伪造百分比 |
| 等待人 | 至少实测一次工具授权或输入请求与合法响应；长工具和等待超过 120 秒保留运行 | 自报“需要授权”不等于有可操作的授权接口 |
| 异常与取消 | 明确启动失败、连接未知、执行失败；能确认取消本工作台拥有的执行 | 释放事项占用不等于停止外部进程 |
| 自动交付 | 正常结束后自动生成待审核材料，来源明确，Agent 不能自行完成事项 | 退出码 0 或模型说“完成”不等于人工验收通过 |
| 恢复 | 页面刷新不丢历史；服务重启先核对已知执行，无法核对则未知且禁止自动重发 | 重新启动服务不代表旧运行已结束 |

### 12.4 证据与最小关联契约

以下是语义要求，先映射现有字段；新增字段、schema 和路由需另行定实现契约，不在规划中提前承诺。

| 信息 | 含义与来源 |
| --- | --- |
| `task_id`、`dispatch_id`、快照哈希 | 工作台生成，固定本次人工确认的需求、目录和目标 Agent |
| `agent_id`、来源实例 | 已登记身份与用户选择的连接，避免不同实例混用 |
| `run_id` 与执行记录标识 | 领取运行及受控进程的本地记录；建立显式映射，不能假设它们是同一个 ID |
| 外部会话、轮次、工具项与请求标识 | 由真实协议回包提供；关联消息、事件和授权响应，缺失时不猜测 |
| 事件标识及关联关系 | 来源协议标识或本地稳定接收标识；重连、重放或重复接收不能重复改变状态 |
| 来源与时间 | 区分运行时事件、桥接器观察、Agent 自报和人工操作；区分来源发生时间与本机接收时间 |
| 最近联系、当前活动、连接状态 | 分别表达桥接连接与真实运行活动，后台计时器不能伪造模型工作或进度 |
| 结果与验证材料 | 保存结果说明、可取得的文件变化、实际命令及退出结果；缺少材料明确显示未提供 |

工作台任务状态继续以 `agent_runs` 为业务事实入口，一个业务运行最多绑定一个底层执行记录；真实进程、轮次、事件、授权和取消由 `execution_runs` 所属执行层提供，投影回业务运行与 `task_events`。不新建第三套并行运行状态，保留既有执行请求的幂等标识；具体映射字段由 Harness 完成实现契约。

命令执行事件和退出码是工具执行证据；是否满足验收仍需核验。文件变化事件不自动证明所有文件都由本次执行产生，已有未提交改动要保留并区分。只有模型文字时标“Agent 自述”，普通 stdout 标“工具原始输出”，不能解析一句“测试通过”就当作真实测试结果。

### 12.5 首个适配器的建议与决策门

双方已对齐先做 Codex 一条真实链，优先审计并复用现有 `execution` 的 app-server 运行基础。原因是此入口适合结构化事件和授权交互；`codex exec` 可以作为非交互能力探测入口，不能通过关闭审批来规避授权实现。DSH 与其他 Agent 继续保留手动交接，待各自的正式执行入口被验证后再加入自动执行范围。

截至本规划，本机仅只读核对版本与帮助：Codex CLI 的非交互、JSONL、目录参数、stdin 与 resume 入口存在，app-server 帮助可用；这不构成真实模型执行、事件覆盖或授权响应的实测证据。支持某个入口也不意味着当前聊天窗口可自动接收任务。

实施前必须补齐：真实环境的认证与版本、发送/接收确认、结构化事件、权限请求与响应、取消行为、异常恢复；既有执行模块能复用多少，由这一步得出。若目标适配器不满足这些条件，标为不支持本 MVP，不能把手动复制包装成自动派发。

官方依据：[Codex 非交互模式](https://developers.openai.com/codex/noninteractive/)说明了 JSONL 事件输出；[Codex app-server](https://developers.openai.com/codex/app-server/)定义了事件及授权交互。实际支持范围仍以选定本机版本的验证记录为准。

| 2 | 人工确认派发与唯一运行关联 | Harness 业务事务/执行装配，Codex 确认界面 | 不复制聊天框即可执行；双击、断线与未知响应不重复启动，快照/运行/来源身份对应 |
| 3 | 自动事件与首页待处理 | Harness 事件归一与持久化，Codex 列表/详情 | 真实活动、等待人、失败、离线可辨；实时记录来源清楚，重读与重连不重复 |
| 4 | 授权、取消及恢复 | Harness 后端装配与持久化，Codex 运行协议及请求界面 | 真实请求只处理一次、过期请求拒绝；取消和服务重启不引发重复执行或伪完成 |
| 5 | 结果待审核与一周试用 | Harness 材料投影，Codex 验收对照，用户最终验收 | 自动交付到待审核、人工完成；真实使用记录证明不再需要搬运任务与进度 |

接入可行性未实测前不承诺固定工期。先完成一个可验收单元再估计后续工作量；不以补齐更多 UI 代替执行闭环。

### 12.7 验收与停止条件

可试用 MVP 交付前完成下面第 1–4 项，并保留实际证据；第 5 项是在交付后的产品价值验收，不增加新的首版功能：

1. 一条真实事项走通“填写 → 确认 → 实际执行 → 自动事件 → 自动提交待审核 → 人工通过”。从确认到待审核期间，人工复制任务和代记进度次数均为 0。
2. 同一运行实际跨过 120 秒，包含一次真实授权或输入等待；既不超时释放，也不自动批准，用户响应正确送达原请求。
3. 双击执行、确认后响应丢失、断连/重启、取消后旧事件和跨项目请求都有验证；不重复启动，不把旧结果写进新运行。
4. 待审核页面能对应原始要求、结果与已取得的命令/文件材料；缺证据明确提示，人未批准时不能完成。
5. 使用一个真实项目连续试用一周，记录任务数、复制次数、人工补记进度次数、需跳回外部窗口的原因及审核时缺少的信息。个人材料仅留本机。

只跑模拟 Agent、合成 JSON 或 CLI 帮助，不能宣布 MVP 成立。如果仍需每条任务复制到聊天框或由人更新进度，闭环验收不通过；应继续解决接入问题，而不是扩大功能。

### 12.8 暂不纳入

首版不要求所有厂商自动接入、接管已有桌面聊天、完整聊天客户端、逐字正文同步、跨 Agent 自动协同、多个 Agent 并行执行同一事项、自动抢领未确认待办、自动审核/合并/发布，以及新的大规模视觉改版。现有手动模式保留为明确的兼容能力，不计作自动执行 MVP。

管理记录与采集材料保存在本机，不等于外部模型离线运行。首次连接应说明目标工具的账号、模型服务、权限和数据流；不承诺所有 Agent 的请求都不离开本机。
